## 1. 本阶段学习与交付

现在已经能查看表和筛选记录，本阶段进一步用SQL回答经营问题。

| 学习步骤 | 要回答的问题 | SQL重点 |
|---|---|---|
| 1 明细 | 每条确认销售产生多少收入和成本？ | JOIN、字段计算、别名 |
| 2 月度 | 公司净收入、毛利、费用和利润是多少？ | 分表GROUP BY、SUM、COALESCE |
| 3 维度 | 哪些商品、渠道和区域贡献最多？ | 分组粒度、比例、DENSE_RANK、HAVING |
| 4 趋势 | 同比、环比、年度累计能否计算？ | 完整月历、LAG、SUM OVER、缺失值 |
| 5 预算 | 实际与预算差多少，差异在哪里？ | 统一粒度、预算版本、NULL、差异方向 |

## 3. 什么是视图

视图保存一个查询定义，可以像表一样SELECT。它帮助重复使用同一套计算口径，不另外存一份销售事实。

原始表→确认销售明细→月度销售/退款→月度财务→公司汇总→报告查询。

例如vw_confirmed_sales_detail已把订单、明细和商品关联，并筛选completed；后续查询不必每次重复写这部分关联。[MySQL视图说明](https://dev.mysql.com/doc/refman/8.4/en/create-view.html)

| 视图 | 一行代表什么 |
|---|---|
| vw_confirmed_sales_detail | 一条已确认销售明细 |
| vw_monthly_sales | 月×商品×渠道×区域的成交汇总 |
| vw_monthly_returns | 退款月×原商品×渠道×区域的退款汇总 |
| vw_monthly_financials | 月×商品×渠道×区域的净收入、净成本和毛利 |
| vw_monthly_expenses | 月×费用类别×部门×归属 |
| vw_monthly_company | 公司一个月的汇总 |
| vw_budget_sales_metrics | 一个版本下的月度销售预算维度记录 |
| vw_calendar_company | 连续月历与公司实际记录；未载入保持未知 |
| vw_sales_budget_comparison | 同一版本和销售维度的实际/预算双方记录 |
| vw_expense_budget_comparison | 同一版本和费用归属的实际/预算双方记录 |

建立后SHOW FULL TABLES会显示10张BASE TABLE和10个VIEW；不应再期待SHOW TABLES总共只有10行。

## 5. 练习2：公司月度经营指标

```sql
SELECT
    month,sales_revenue,refund_amount,
    net_revenue,net_cost,gross_margin,
    expense_amount,operating_profit,confirmed_orders
FROM vw_monthly_company
WHERE month='2026-09-01';
```

核对：

```text
折后成交收入4150 − 退款910 = 净收入3240
成交成本2615 − 成本转回560 = 净成本2055
净收入3240 − 净成本2055 = 毛利1185
毛利1185 − 费用400 = 经营利润785
已确认订单数8
```

销售和退款先各自汇总，再连接；两次退款不会复制销售收入。公司订单数从明细里的订单号去重，不能把每个商品的订单数直接加总。

业务视图保留原始事件月。直接查询10月会看到退款边界，不能称为10月完整经营结果；完整范围报告见02_detail_and_monthly.sql。

## 6. 练习3：商品、渠道和区域

先看商品：

```sql
SELECT
    product_id,
    SUM(net_revenue) AS revenue,
    SUM(gross_margin) AS margin,
    CASE WHEN SUM(net_revenue)>0
         THEN ROUND(100*SUM(gross_margin)/SUM(net_revenue),2)
    END AS margin_pct
FROM vw_monthly_financials
WHERE month='2026-09-01'
GROUP BY product_id
ORDER BY revenue DESC;
```

| 商品 | 净收入 | 毛利 | 毛利率 |
|---|---:|---:|---:|
| P001收纳盒 | 2940 | 1050 | 35.71% |
| P003厨房置物架 | 240 | 105 | 43.75% |
| P002清洁刷 | 60 | 30 | 50.00% |

比例从合计分子与分母计算。清洁刷毛利率最高，但收纳盒贡献的毛利金额最多，这两种排序回答不同问题。

把SELECT和GROUP BY中的product_id都改为channel_code，再改为region_code，观察分组粒度变化：

| 渠道/区域 | 净收入 | 毛利 |
|---|---:|---:|
| C01/R01 | 2390 | 850 |
| C02/R02 | 610 | 230 |
| C03/R03 | 240 | 105 |

本小样本渠道与区域恰好对应，不表示两者在完整数据中总是一一对应。完整排名、窗口排名和HAVING示例见[03_dimension_analysis.sql](../../../sql/stage4/03_dimension_analysis.sql)。

## 7. 练习4：同比、环比与累计

先在当前mysql连接中加载参数，然后执行趋势文件：

```sql
SOURCE sql/stage4/00_parameters.sql;
SOURCE sql/stage4/04_trends.sql;
```

这两个SOURCE命令要求MySQL从项目根目录启动。若不确定当前目录，可以重新在PowerShell执行Set-Location后登录。

当前结果：净收入3240；上月收入、上年同月收入、环比、同比、YTD均为NULL；sample_loaded_cumulative_revenue为3240。

原因是样本只完整载入9月。日期表虽然包含2024—2026全部月份，不能据此把未载入的经营数据当作0；也不能把9月样本合计叫全年累计。

LAG取排序后的前一行；因此先构建连续月历，LAG(...,1)才对应上一个自然月，LAG(...,12)才对应上年同月。基期为0或负数时，常规增长率不计算。[MySQL窗口函数说明](https://dev.mysql.com/doc/refman/8.4/en/window-function-descriptions.html)

SQL关键语法：

```sql
LAG(net_revenue,1) OVER (ORDER BY month)
SUM(net_revenue) OVER (
    PARTITION BY YEAR(month)
    ORDER BY month
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

前者取上个月，后者逐月累加本年已知金额。YTD还需检查年初至所选月份均在完整覆盖范围内。历史日期测试已在临时验证数据中通过；这些合成交易没有加入你的业务样本。

## 8. 练习5：实际与预算

执行[05_budget_analysis.sql](../../../sql/stage4/05_budget_analysis.sql)，先看销售维度表，再看费用和公司合计。

| 公司指标 | 实际 | 预算 | 实际−预算 |
|---|---:|---:|---:|
| 净收入 | 3240 | 3380 | -140 |
| 毛利 | 1185 | 1280 | -95 |
| 费用 | 400 | 380 | +20 |
| 经营利润 | 785 | 900 | -115 |

收入完成率95.86%。净收入差异分别来自：厨房置物架C03/R03少80元，收纳盒C02/R02少50元，收纳盒C01/R01少10元，清洁刷无差异。

公司利润差异=毛利差异−费用差异=−95−20=−115元。这里只解释金额构成，不直接证明市场、活动或供应导致了变化。

费用：营销与人工各超10元，平台佣金超5元，物流节省5元，管理费持平，合计超20元。收入高于预算通常有利；费用高于预算通常不利。

缺失预算保留NULL和MISSING_BUDGET；零预算有记录、金额为0，但完成率为空。某实际维度缺少预算时，对应公司预算合计标为NULL，避免部分预算与全公司实际比较。预算版本参数的文字比较规则已与原表统一。
